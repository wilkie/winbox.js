## Observed behaviour

- [[measured]] [[probe:kowner]], by ordinal through `GetProcAddress`: the probe's module for its data segment and its code segment, its module's database and a block it allocated with `GMEM_SHARE`; its prefix (`GetCurrentPDB`) for a moveable block it allocated, by handle or by selector; the task itself for the task's database; USER's module for USER's data segment (ordinal 285's answer); nought for the prefix, for nought and for a selector that is no block's. After [[fn:KERNEL.K403]], the owner it set.

## Inside Windows

- [[read out]] `KRNL386.EXE` seg1 `29ae`-`29bc`. One word, a selector, popped. It calls KERNEL's own routine at seg1 `29bf`. That routine finds the block's arena through the selector table, entry selector ÷ 8 of the table whose length is at 22Eh and whose linear address is at 230h ([[fn:KERNEL.THHOOK]], routine seg1 `297c`). It answers the arena's word at 12h, or nought where the selector is past the table.
- [[read out]] `KRNL286.EXE` seg1 `267f` does the same over its own arenas, a paragraph before the block, where the owner is the word at 1 (seg1 `2690`-`26a0`).
- [[read out]] The owner is what KERNEL's own code asks for: [[fn:KERNEL.HasGPHandler]] and [[fn:KERNEL.PatchCodeHandle]] ask it of a code segment to find its module (seg1 `4c7b`, `7bce`).

## Callers

- No file of the installations or the corpus imports it or holds its name (`kb/data/kernel-callers.json`). Its partner is [[fn:KERNEL.K403]].

## Implementation

In both engines (`src/win16/kernel/block-owner.ts`; the Rust engine's `crates/winbox-win16/src/kernel_calls/owners.rs`): an owner [[fn:KERNEL.K403]] set, while the block is there; else the block as TOOLHELP's `GlobalEntry` sees it ([[topic:tool-helper]]) -- its owner, made the task's prefix for a block of a task's; nought for no block. WinBox keeps the prefix in no block of the global heap, which is nought as Windows answers.

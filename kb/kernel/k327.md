## Observed behaviour

- [[read out]] `KRNL386.EXE` seg1 `949b`-`94c4` (`KRNL286.EXE` seg1 `8c6d`). It takes its arguments in registers: BX the error code, CX:AX the bad value. It is reached by a far jump, with a far return address on the stack.
  1. It calls [[fn:KERNEL.LogParamError]] with the code, the return address (the place the check failed) and the value (`949e`-`94aa`). In the retail build that tells a debugger through `INT 41h` if one is there, and otherwise does nothing ([[topic:kernel-queries]]).
  2. If the code has bit 15 set, a warning, it returns where it came from, and the check goes on (`94af`-`94b2`).
  3. Otherwise it unwinds the API's frame: it drops its own return address, takes the next word as the offset to return to and the word after as the caller's BP, clears BP's low bit (the far-frame mark), and returns there with AX, DX, CX and ES nought (`94b4`-`94c4`).
- [[read out]] The checking code sits in each module's own segments. For example, a USER function (USER seg11 `03eb`) pushes BP and then the offset of its own `RETF 8` (`push 40Eh`). It calls a near check (seg11 `0435`) for each pointer. A check that finds a bad pointer puts the code in BX (7008h for a bad pointer, 6022h for a bad handle) and the value in CX:AX. It makes its near return into a far one (`pop dx; push cs; push dx`) and jumps to KERNEL's ordinal 327 (USER seg1 `aee2`-`aeed`, seg11 `0411`-`0414`). KERNEL's own [[fn:KERNEL.SwapRecording]] does the same through seg3 `01a2`.
- [[inferred]] So a call with a bad parameter returns nought from the API at once, its arguments popped by the API's own `RETF`, and the debugging build would print the code. That is the "parameter validation" of Windows 3.1's USER, GDI and KERNEL.
- Not yet measured. The visible half, nought for a bad pointer, is measured case by case on the USER and GDI pages that cover their parameter checks.

## Callers

- [[read out]] `USER.EXE` and `GDI.EXE` import it by ordinal, from many checking stubs (USER segments 1, 10, 11, 12, 14 and others; GDI's likewise). No other file of the installations or the corpus imports it (`kb/data/kernel-callers.json`).

## Implementation

A stub in both engines. WinBox's USER and GDI are its own and check their parameters in their own code, answering what Windows answers where a probe has shown it.

**Recommendation: not needed.** Only USER and GDI call it, and WinBox replaces both. A third-party library compiled against it would be the only reason; none is in the corpus. If one appears, the behaviour is short to write: report nothing, return to the check for a warning, otherwise unwind as above and return nought. That is about 20 lines of register handling in each engine. See [[topic:kernel-internals]].

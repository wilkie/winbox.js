WATCOM C's Win386 extender makes a 32-bit program of a Windows 3.1 one: its 32-bit code is linked as a `.rex` image (`wlink system win386`), and `wbind` puts a 16-bit program in front of it, the supervisor (`binw/win386.ext`), which Windows loads as any NE program. A library is bound the same way to the library supervisor (`binw/w386dll.ext`, `wbind -d`). Sierra's `SMACKE16.DLL`, which Lode Runner: The Legend Returns' setup loads, is such a library. The supervisor needs a 32-bit DPMI host, which only 386 enhanced mode has ([[guide:enhanced-mode]]); in standard mode it shows "Not running on a 386 DPMI implementation" ([[topic:global-and-local-memory]], "DPMI's version").

## The probes

[[measured]] The probes are built by `build-probes.mjs` from `oracle/probes/win386/` (`buildWin386`): a program with `wcc386 -bt=windows`, `wlink system win386` and `wbind -n`; its library, `<name>.dll.c`, the same way with `-bd` and `wbind -d`, as `<NAME>D.DLL`; a source that defines `PROBE_WIN16` is a 16-bit program, built as the other probes are. `fetch-toolchain.mjs` takes `binw/win386.ext`, `binw/w386dll.ext` and `lib386/` from the Open Watcom package it already fetches. They are built into `oracle/build/win386/`, apart from `oracle/build/probes/`.

A Win386 probe is recorded in 386 enhanced mode alone. `record.mjs` reads `oracle/build/win386/` only with `--mode enhanced`, so a plain run of every probe never starts one, and names one of them without it is refused: in standard mode the supervisor would wait at its box until the recorder's timeout.

- [[probe:w386ver]]: a Win386 program's pointers are 4 bytes, it sees `GetWinFlags` `0C29h`, and the C library gives it a block of 2 MB.
- [[probe:w386env]]: what the supervisor leaves the 32-bit program, as the program reads its own selectors with `LAR` and `LSL`.
- [[probe:w386dpmi]]: the supervisor's DPMI calls, made again one at a time with the arguments it gives them, from a 16-bit program.
- [[probe:w386lib]]: a 16-bit program that loads a Win386 library and calls its 32-bit code.

## What the supervisor does as it starts

[[read out]] `W386VER.EXE` seg1, the supervisor as `wbind` binds it (the offsets are the bound program's; every Win386 program of this Open Watcom carries the same code):

- **Its entry** (`5180`-`5240`): `InitTask`, `WaitEvent`, `InitApp`, `GetVersion` (DOS's version through INT 21h 30h as well), `GetModuleFileName` of its own file, and its C runtime's start; then its `WinMain`.
- **The host** (`0077`-`009f`): `GetWinFlags`, kept, and DPMI 0400h; BX's bit 0 clear, the box "Not running on a 386 DPMI implementation" captioned "Open Watcom Win386" (`02e0`-`02fa`, `MessageBox` with `MB_TASKMODAL` and `MB_ICONSTOP`), and nothing more.
- **Its own file** (`00af`-`01b8`): `GetModuleFileName`, then the file opened with INT 21h 3Dh, the offset at 38h read and followed, a flag at `12C4h` set unless the segment of its first entry starts with the words `DEADh` and `BEEFh` (`0106`-`011d`, `0316`; what reads the flag is not followed), and the 32-bit image's header, `MQ`, read from the file (`014a`-`0156`): its size, its stack and its relocations.
- **Its memory** (`3768`-`3797`): one block from 0501h for the image, 64 KiB more than it needs. The 32-bit segments' base is 64 KiB into it (`039e`-`03ad`).
- **Its selectors** (`3688`-`3765`): 0003h's increment; a code selector from 0000h and two data selectors in a row, each given its base (0007h), the rights of 32-bit code or data at the caller's privilege -- `C09Bh` or `C093h` with the granularity bit for a limit past 1 MB, `409Bh` or `4093h` without (`3624`-`3686`) -- and a limit of FFFFFFFFh (0008h). Then 000Bh of the first data selector: a limit whose four high bits and low word are all set is taken for 4 GiB (`3707`-`372f`). The second data selector is the stack's.
- **Its image**: read into the block and its relocations applied, each a double word added through ES:EDX with a 32-bit address (`0850`-`088a`).
- **Aliases** (`39b8`-`3a0e`): fifty selectors from 0000h, each given `F3h` and a limit of FFFFh, for 16-bit pointers to the 32-bit memory; one more for each block the program asks for (`342a`-`34ab`).
- INT 2Fh FA00h-FA21h only where its debugging flag is set (`07a5`-`07ea`, `08ff`-`090b`) [[inferred]]: a debugger's interface, not called in a plain run.

[[measured]] [[probe:w386dpmi]], in 386 enhanced mode: WIN386 answers every call of that order with the carry clear. 0501h's block is on a page; 0003h is 8; each 0000h answers a local selector at privilege 3; the code selector reads back as access `FBh`, flags `CFh` and limit `FFFFh` in its low word, the data selectors `F3h` and `CFh`, so the supervisor's test finds 4 GiB; 0006h answers the base set; the aliases read back `F3h`, flags nought, limit `FFFFh`. A byte written through the flat data selector with a 32-bit address is read back through an alias of the same base.

## What the 32-bit program finds

[[measured]] [[probe:w386env]], from the 32-bit code:

- **CS**: rights `00CFFBh` -- `LAR` of a double word answers the descriptor's second double word masked with `00FFFF00h`: the access byte `FBh`, then the granularity byte whole, `CFh`, its flags and the limit's top four bits -- and a limit of FFFFFFFFh.
- **DS and ES**: `00CFF3h`, FFFFFFFFh, the same selector. **SS**: the same rights and limit, another selector: the second of the pair.
- **FS** is the null selector; **GS** the supervisor's own data segment, the program's 16-bit one, `F3h` and its size for its limit (4E5Fh).
- **The stack**: ESP is `1FB4h` at `WinMain`, and a push moves it by 4: a 32-bit stack.
- `AllocAlias16` gives a 16-bit selector, `F3h`, limit FFFFh.

## Libraries

[[read out]] `W386LIBD.DLL`, bound to `w386dll.ext`, exports `DLL1` to `DLL128`, each a 16-bit entry for the 32-bit routine of that number, `WEP`, and `Win386LibEntry` (ordinal 130), in that spelling. `SMACKE16.DLL` exports the same, its last as `WIN386LIBENTRY`. The 32-bit side's `WinMain` runs as the library is loaded and names its routines with `DefineDLLEntry`.

[[measured]] [[probe:w386lib]]: `LoadLibrary` gives an instance; `GetProcAddress` finds `DLL1`-`DLL3`, not `DLL129`, and not `Win386LibEntry` by that name or by `WIN386LIBENTRY`; by its ordinal it is found. Routine 1 through `DLL1` adds its two double words and a word (100,004); through ordinal 130 with the routine's number last, the same (70,003). Routine 3 calls `GetWinFlags` from the 32-bit side after a block of 100,000 bytes from the C library, `0C29h`. After `FreeLibrary` the module is gone.

[[read out]] Why `Win386LibEntry` is not found: `GetProcAddress` (`KRNL386.EXE` seg2 `073f`) copies the name asked for without changing its case (`0706`-`073c`, DX nought) and seg1 `50ca`-`50fc` compares it with each name of the module's tables, upper-casing the name asked for character by character (`83e9`) and comparing it with the table's as the module keeps it. A name kept in mixed case is never found by name. Both engines find a name so now (`ordinalFound`, `ordinal_found`); they compared both sides without regard to case before. A name beginning with `#` is the ordinal its digits make (`50b3`-`511c`); WinBox does not follow that yet.

## In WinBox

Both engines run Win386 programs and libraries in a machine in enhanced mode: [[probe:w386ver]], [[probe:w386dpmi]] and [[probe:w386lib]] agree whole, and [[probe:w386env]] but for GS's limit, which is a program's data segment's ([[topic:global-and-local-memory]], "Not yet done"). The supervisor's DPMI calls are phase 3's ([[topic:dpmi-functions]]); what it needed beyond them was the processor's:

- **A 32-bit stack** (the B bit). [[documented]] With the stack segment's B bit set, the 80386 takes ESP for every push and pop, call and return, interrupt frame, `IRET`, `ENTER` and `LEAVE`, and the stack's own accesses have 32-bit offsets, whatever the instruction's operand and address sizes; with it clear, SP alone moves and wraps in 64 KiB, ESP's high word left (Intel's _80386 Programmer's Reference Manual_, "StackAddrSize"). The Rust core left such a stack to its host, and natively that load was a fault; it now runs it (`stack32`, `crates/winbox-cpu`). 
- **Segments of 4 GiB.** The Rust core kept one past a segment's limit in 32 bits, and a limit of FFFFFFFFh made nought: no room, every access a fault. It keeps it in 64 bits now. A linear address wraps at 4 GiB in both cores.
- **`LAR` and `LSL` of a double word**, as [[probe:w386env]] recorded them.
- **`TEST` of a byte** (F6h /0) under the operand prefix.

[[measured]] The hardware vectors hold every change: the 80286's and the 80386's suites, all 941 files, pass as before in both cores (`pnpm test:conformance`; `cargo test -p winbox-cpu --test conformance`). Neither suite has a 32-bit stack, which needs protected mode; both cores' own tests run one (`a_32_bit_stack_moves_esp_whole`, "a 32-bit stack, its B bit").

## Lode Runner: The Legend Returns

[[measured]] The owner's disc, its setup in a machine in enhanced mode, on the VGA's 256 colours, in both engines (`test/layers` harness, not committed; the disc is not in the repository): `SETUP.EXE` starts `_SETUP.EXE`, which loads `SMACKE16.DLL` and finds `Win386LibEntry` (its name in capitals, so `GetProcAddress` finds it); the supervisor starts the library's 32-bit code with the calls above. `SETUPL.DLL` and `EREGLIB.DLL` are loaded and the Sierra Setup's "Main Menu" is drawn whole: its bitmaps are `SETUPL.DLL`'s, which it asks for as `#164` to `#173`.

- [[read out]] A name beginning with `#` given to `FindResource` is the number its digits make, to the first that is not a digit, in a word; one that makes nought is a name (`KRNL386.EXE` seg3 `0ac0`-`0af6`, called from `0964` for the type and the name). Both engines read it so now (`numbered`, `named`); before, the setup's menu was a blank dialog.
- `SETUP.EXE` and `_SETUP.EXE` are both the module `SETUP`. The Rust engine's `GetExePtr` found a module's own handle only in its chain of modules by name, which holds one of the two, so `_SETUP`'s `SetWindowsHookEx` with its module's handle was refused and MFC faulted creating its window; `GetExePtr` takes any module's handle now (`KRNL386.EXE` seg1 `4e7f`-`4e8d`: an odd handle whose segment starts with `NE`).
- Install, then the setup's "System Test" box. What comes after is in "Not yet done".

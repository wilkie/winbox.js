This page is a plan, in part built: phase 1, the replay's parity (1a) and the unit tests' audit and ports (1b, [[guide:retire-typescript-tests]]), and phase 2, the generators and the knowledge base, are done (2026-11-08); phases 3 to 5 are not. It follows the model of [[guide:enhanced-mode]].

On 2026-11-08 the owner decided to retire the TypeScript engine. Its current form is kept on the local branch `typescript-engine`, made at `9b221155` (develop's tip that day). From then on develop has one implementation, the Rust engine. The oracle's recordings stay the ground truth: `oracle/fixtures`, recorded under DOSBox. Keeping two engines twinned, with every fix made in both and the corpus compared between them, has stopped being worth what it costs.

"The TypeScript engine" means the emulator: the CPU core, DOS, the Win16 modules, the raster engine, and the jest tests that drive them (the oracle replay's shards, the corpus survey, the unit tests). These stay in TypeScript or JavaScript:

- the web page (`src/run`, React and MUI) and its build;
- the oracle's scripts (`scripts/oracle`);
- the knowledge base's site (`scripts/kb`);
- the asset bundle's maker (`src/assets`, `scripts/assets`).

Every figure below was measured on `9b221155`. Line counts are of tracked files; the import graph was walked from each entry point along value imports. Type-only imports were walked separately and are noted where they matter.

## Coverage parity

### The oracle's replay

The two engines check the recordings differently.

- **TypeScript** (`test/oracle/conformance.ts`) replays every fixture at the top of `oracle/fixtures` (730) and the 17 in `oracle/fixtures/enhanced` that `ENHANCED` names: 747 fixtures, 314,075 records. A probe named in `RUN_WHOLE` (449 probes, 505 fixtures) is run whole. The other 242 fixtures are replayed record by record through an adapter that calls the engine directly. Each function of each fixture is one test, and every record of it must agree, unless `KNOWN_GAPS` names it (69 entries, on 52 fixtures). In that case the test is `it.failing`, so a gap that starts to agree fails until it is taken off the list. A function with no adapter (`unsupported`) or a stub (`unimplemented`) passes with nothing checked: 49 fixtures have 17,000 records with no adapter, and `wingapi` has 9 that reach a stub. In all, 296,272 records agree, and 647 fixtures agree on every record with no gap open.
- **Rust** (`crates/winbox-win16/tests/probes.rs`) runs each fixture named in `AGREEING` (350: 341 at the top level and 9 in `enhanced/`) whole, and asserts that its records equal the recording, all of them. Nothing else is checked by `cargo test`. The survey (`survey`, `--ignored`, a merge gate) runs every fixture it finds, standard and enhanced: 764 of them. It compares only how many records agree with the TypeScript engine's count in `conformance.json`, and fails no test: a gate reads "ended behind the TypeScript engine" from its output.

[[measured]] The survey was run on `9b221155` with one line printed for each fixture (445 seconds), and joined with `conformance.json` and the lists. Then `differing` was run on the 52 fixtures with gaps:

- **No fixture is missing from the Rust engine.** It runs all 747 that the TypeScript replay loads, and 17 more in `enhanced/` that `ENHANCED` leaves out: 764. Every run ends.
- **The Rust engine is never behind.** On each of the 747 it agrees on as many records as the TypeScript engine, or more: 702 level, 45 ahead, none behind.
- **Whole fixtures.** All 647 fixtures that the TypeScript engine agrees with on every record, with no gap open, are whole in the Rust engine too. The Rust engine is whole on 677, 30 more than TypeScript: 29 that the TypeScript replay cannot run, or runs only in part (displays other than the VGA, the sound card's installations, `palshot`, `mapcpl`, `wavemix`, `sysdirs`) and `enhanced/mmmisc`.
- **The fixtures with gaps.** In 50 of the 52, the Rust engine differs from Windows in exactly the functions `KNOWN_GAPS` names, and the counts are equal. In `nullds` and `regmsg` it differs in the gap's function and also in functions the TypeScript replay has no adapter for (`nullds`'s `calls`, `counter`, `ds` and `read`). It never differs in a function the TypeScript replay holds.
- **What neither engine holds.** 18 fixtures that the TypeScript replay runs only in part (`stack`, `scalemem-vga` and `-ega`, the Ad Lib probes, `groundsc-vga`, `wavedev`, `mididev`, `mciplay`, `seqlen`, `scalepts-ega`, `freemem`, `environ`, `enhanced/freemem`): the Rust engine differs in 13,281 of their records, which the TypeScript replay counts as "no adapter". Also the 16 enhanced recordings that only the Rust survey reads and that are not whole (`enhanced/stack` 730 of 3,650, `enhanced/prttrot` 56 of 331, and 14 short of a record or a few: [[guide:enhanced-mode]], "Not yet done"). `wingapi`'s 9 halftone-brush records are a stub in both engines (`STUBBED`).

**The shortfall** is not in agreement. It is in what `cargo test` holds:

|                                        | TypeScript replay | Rust `cargo test` |
| -------------------------------------- | ----------------: | ----------------: |
| Fixtures held                          |               747 |               350 |
| Records held to agreement              |           296,272 |            36,487 |
| A known gap that starts to agree fails |               yes |           no list |

Records the TypeScript replay holds that no Rust test holds:

- 316 fixtures the TypeScript engine agrees with whole (125 run whole, 191 through adapters), 251,066 records;
- the 52 fixtures with gaps, 11,512 records outside their gaps;
- the agreeing parts of `freemem`, `enhanced/freemem`, `sysdirs` and `wingapi`, 68 records.

That is 372 fixtures and 262,646 records. The Rust engine agrees on every one of them today, so it can take them all over without naming a single Rust gap for them. The 327 fixtures the Rust engine runs whole but `AGREEING` does not name can be held at once. The 69 `KNOWN_GAPS` entries move across unchanged.

### How the Rust engine takes over the replay

Before any TypeScript replay is deleted, the Rust engine gets a replay that checks at least what the TypeScript one checks, and in the same way:

1. **One trial per fixture, every fixture.** A new test, `crates/winbox-win16/tests/conformance.rs`, finds every fixture as the survey does (the top level and `enhanced/`) and runs each probe whole once. It then holds each function's records to the recording, as `conformance.ts` does. It uses `harness = false` with `libtest-mimic`, a dev-dependency, so that each fixture is a named trial that runs in parallel and can be picked out (`cargo test --test conformance -- prtt`), as `-t "<probe> against"` picks out a shard's test. The `AGREEING` list stops being needed: every fixture is held, and only its known gaps are excused.
2. **Known gaps in Rust.** `KNOWN_GAPS` moves to `tests/support/mod.rs` with its reasons, keyed as it is now (`probe:function`, `probe-display:function`, `enhanced/probe:function`). A gap that agrees fails its trial, so the list only shrinks. A fixture where the Rust engine agrees on fewer records than the TypeScript engine is not dropped. Each function it gets wrong becomes a named Rust gap, with the reason found by the same rule as any gap (read out or recorded), and is listed in this page's Not yet done until it is closed.
3. **No silent passes.** The TypeScript replay passes a function it has no adapter for. The Rust replay runs every probe whole, so there is no adapter to be missing. A probe that is not built, or a fixture whose program will not start, is a failure, unless an `UNBUILT` list names it with a reason. That list is the Rust replay's only "unsupported".
4. **The report.** The trial writes each fixture's line in `conformance.json`'s present shape (`probe`, `display`, `windows`, `records`, `functions` with `total`, `agreed`, `disagreed`, `unimplemented`, `unsupported`, and `gaps`). `unimplemented` counts records whose call reached `Stop::Missing` or a stub (`export.stub`); `unsupported` counts `UNBUILT`'s. After a full run, the shares are merged into `kb/data/conformance.json`, as `test/global-teardown.ts` merges jest's.
5. **The survey.** `typescript_agreed` goes. The survey then compares a run with the last `conformance.json`, which is now the Rust engine's own, so "behind" means "behind its own last report".

Proof that nothing is lost, before the TypeScript replay is deleted:

- the two `conformance.json` files are set side by side: the one the TypeScript replay last wrote, and the one the Rust replay writes. For each fixture and function, Rust's `agreed` must be at least TypeScript's, or the function must be a named Rust gap;
- every `KNOWN_GAPS` key in `replay.ts` is in the Rust list, or is closed in Rust, which the survey's "ahead" shows;
- `pnpm kb` builds against the Rust report. Its evidence check holds every page marked `exact` to its probes' records, so a page whose probe is now only partly agreed fails here, not later.

## The owner's decisions

The owner decided on 2026-11-08 to retire the TypeScript engine. Its last form is the branch `typescript-engine` (9b221155). The answers to the questions below, given the same day:

- **Gates (question 1):** the Rust replay is a release-profile gate, run in parallel, in place of the full jest run. `cargo test --workspace` keeps a quick sample.
- **Records neither engine holds (question 2):** they become named Rust gaps, each with its reason. The 16 enhanced fixtures stay out of `conformance.json` until the knowledge base tells the two modes apart.
- **Library, hybrid and benchmarks (questions 3 and 4):** retired. `pnpm build` becomes the page's build, `cargo doc` replaces `typedoc`, `crates/winbox-wasm` and `bench/` are deleted, and a `winbox-cpu` bench measures CPU speed.
- **Signatures (question 7):** frozen into `kb/data/signatures.json` before phase 4. Summaries come from Rust doc comments.
- **Questions 5 and 6:** the recommendations stand. The page says the engine is not built, and `pnpm dev` builds it first. The owner pushes and tags the branch.

## Open questions for the owner (answered above)

1. **The replay's place among the gates.** [[measured]] The survey runs every fixture serially, in release, in about seven minutes on a quiet machine (the 2026-11-05 gate log: 420 seconds). The jest shards ran in parallel inside the 618-second jest run. Should the Rust replay be part of plain `cargo test --workspace`, in debug and so much slower, or a release-profile gate like the survey is? Recommendation: a release gate, `cargo test --release -p winbox-win16 --test conformance`, run in parallel trials, and in the merge gates in place of the full jest run. `cargo test --workspace` keeps a quick sample of fixtures.
2. **The records neither engine holds today.** Parity costs no Rust gaps: the Rust engine agrees wherever the TypeScript engine does. But a replay that holds every fixture also meets two groups that no test checks now. One is 13,281 records in 18 fixtures that the TypeScript replay passes as "no adapter" and the Rust engine gets wrong (`stack`, `scalemem`, the Ad Lib probes and the rest above). The other is the 16 enhanced recordings outside `ENHANCED`. The TypeScript replay left the second group out because the knowledge base's evidence check would count enhanced-mode records against pages measured in standard mode. Recommendation: hold both groups in the Rust replay, each function as a named gap with its reason. Leave the 16 enhanced fixtures out of `conformance.json`, as now, until the knowledge base tells the two modes' records apart.
3. **The library build and type documentation.** `pnpm build` makes `dist/winbox.js`, the TypeScript engine as a library that sets `window.Win16`, and `package.json` publishes it as the package's entry. Nothing in the repository imports it. Recommendation: retire the library build and the package entry, make `pnpm build` the page's build, and replace `typedoc` with `cargo doc` for the engine.
4. **The hybrid core and the benchmarks.** `crates/winbox-wasm` exists only to run the Rust core inside the TypeScript machine, and `bench/wasm.mjs` measures that boundary. The CPU speed gap to DOSBox has been measured with `bench/cpu.ts`. Recommendation: delete the crate and `bench/` with the engine, and measure the Rust core's speed with a `winbox-cpu` bench on the same workloads, native and in the browser through `winbox-web`.
5. **The page without a built engine.** Today the page falls back to the TypeScript engine where `target/winbox-web` is missing, and the e2e test "runs on the TypeScript engine where the Rust engine has not been built" holds that. Afterwards the page can only say that the engine is not built. Recommendation: the page shows that, and `pnpm dev` runs `pnpm build:web` first when the module is missing or older than the crates.
6. **The `typescript-engine` branch.** It is local. Pages and comments will cite it as the record of what the TypeScript engine did. Recommendation: push it to the remote and tag its tip (`typescript-engine-final`), and cite the tag.
7. **Typed signatures in the knowledge base.** The pages' "Signature" parts come from TypeScript JSDoc (`@param {Type} name`). Rust doc comments have no such convention: the arguments are read from `Args` in the body. Recommendation: before phase 4, freeze the signatures the JSDoc gives today into `kb/data/signatures.json` (the project's own text, not Windows'), keep them there from then on, and take only the summary from the Rust doc comment.

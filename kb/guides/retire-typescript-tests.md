This page is the audit [[guide:retire-typescript]] asks for under "Unit-test areas", done on 2026-11-08 (phase 1b). It covers every TypeScript test file under `test/emulator`, `test/dos`, `test/raster`, `test/win16`, `test/file-systems`, `test/layers`, `test/assets` and `test/run`, and `test/oracle/ordinals_test.ts`. The CPU vectors' baselines and the writers of the caribb, widget and accessible-tree fixtures are phase 1a's, not this page's.

Each case gets one disposition:

- **(a) held.** A named Rust test or probe already holds the same behaviour.
- **(b) ported.** Ported to Rust exactly, with its citation kept.
- **(c) page.** Page code that stays in TypeScript. Its test was reworked so that it no longer needs the engine, onto a bare disk image or committed fixture data.
- **(d) engine-internal.** A detail of the TypeScript engine with no Windows or hardware behaviour behind it, so nothing replaces it. The reason is given.

## What the ports found

The rule was the guide's: where the Rust engine disagrees with a TypeScript test, the expected value is kept, and the evidence decides which engine is right. The Rust test stays, marked `#[ignore = "finding: …"]`. None of these is fixed in phase 1b.

- **An expand-down segment, read above its limit.** [[documented]] The Intel 386 manual says offsets from limit + 1 to FFFFh are inside an expand-down data segment. Rust's `descriptor` gives such a segment no room, and the engine stops with `Fault(13)` (`crates/winbox-cpu/tests/units.rs` `protected_mode::expand_down::allows_an_access_above_the_limit`). The TypeScript engine reads.
- **An expand-down segment, read below its limit.** [[documented]] The 80386 raises #GP(13). Rust's `fault_vector` answers None for the segment, so the engine stops instead of raising the fault (`crates/winbox-win16/src/fault_vector.rs` `an_expand_down_segment_faults_below_the_limit`).
- **An instruction fetched past CS's limit.** [[documented]] The 80386 raises #GP(0), and the TypeScript engine raises 13. Rust's `decode` reads code bytes only within the limit, so `fault_vector` answers None and the engine stops (`fault_vector.rs` `faults_when_instruction_fetch_runs_past_the_code_segment`).
- **WIN87EM's emulator.** The TypeScript engine carries out a floating-point instruction after `INT 34h`–`3Dh` when the coprocessor is switched off. The Rust engine had no emulator and stopped (`Stop::Unsupported("the floating-point emulator")`), and three tests in `crates/winbox-win16/tests/win87em.rs` were ignored for this. The OS fixups themselves agree. Done (2026-11-09): the Rust engine's emulator follows WIN87EM's read-out, [[probe:fpemu]] records it on Windows without a coprocessor, and the three tests pass ([[topic:floating-point]]).
- **The task's environment under DOSBox.** [[measured]] [[probe:environ]] records `PATH`, `COMSPEC` and `BLASTER` before `windir`, with the count at 75. The Rust engine gives `windir` alone (`tests/task_environment.rs` `a_task_environment_puts_windir_after_the_dos_hosts_variables`). This is one of the records the guide's "What neither engine holds" names for `environ`.

Elsewhere the Rust engine agreed with every expected value the TypeScript tests held. In the fabricated recordings the counts were equal on every ceiling. On `glyphs-cour-stubs` the Rust engine gets every cell right, where the TypeScript test allowed 36 wrong.

One finding concerns the TypeScript side. [[measured]] `dump-exports.mjs` checked 911 ordinals against the SDK's import library. Reading `kept.rs`, it checks 926, and none disagrees. The old parser had lost KERNEL's ordinals 343 to 356 and 403 to 404. An apostrophe in a comment ("KERNEL's own table", at 342) opened a quoted string that swallowed those entries.

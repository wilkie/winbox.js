This page is a design, with a prototype and the first pass. The prototype is built: `scripts/catalog/catalog.mjs` writes the catalog, `scripts/catalog/sample.mjs` takes ten games of it through the pipeline once (2026-11-14), `scripts/catalog/titles.mjs` finds titles from the programs themselves (2026-11-14), `scripts/catalog/wikipedia.mjs` matches the catalog to Wikipedia's list, and `pnpm kb` builds the table with its ratings (2026-11-14). The first pass is built and has run over the whole catalog (2026-11-14, below, "The first pass"): `scripts/catalog/fetch.mjs` fetches every item, `scripts/catalog/needs.mjs` reads what each needs, `scripts/catalog/runtimes.mjs` fetches the runtimes it places (Visual Basic's, Klik & Play's, Borland's controls), and `scripts/catalog/pass.mjs` installs, runs and classifies each, and writes `catalog/results.json` and the work queue, `catalog/queue.json`. It follows the model of [[guide:launcher]] and [[guide:enhanced-mode]].

The corpus (`corpus/README.md`) is some forty programs, chosen for what they exercise and held to what Windows recorded of them under DOSBox, call for call and pixel for pixel. It finds what the probes did not think to ask. A compatibility database is wider and shallower: every Windows 3.x program that can be found, each tried once, with a one-word answer and the reason. It says which programs run, and it turns the ones that do not into a list of gaps, the most common first. A program it turns up that needs a closer look goes into the corpus, and is held to the oracle from then on.

## The catalog

The catalog is a committed file of metadata, one entry for each program. It never holds a program's files, its screens or its call logs: like the corpus's manifest, it says where a program is published and how to check the bytes, and nothing more.

It is `catalog/catalog.json`, at the top of the repository. It is not in `corpus/`, because everything there but the manifest and its README is ignored, and because the two lists differ: the corpus is a sample held to the oracle, and the catalog is everything published. An entry that joins the corpus is copied into `corpus/manifest.json` with its `run`, `survey` and SHA-256, as now.

### What a program needs

These are found from the program's own files where possible, before it runs, and checked against the run where not:

| Need                            | How it is found                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Mode** (standard or enhanced) | A WATCOM Win386 program or library is bound to the Win386 supervisor, which refuses standard mode with "Not running on a 386 DPMI implementation" ([[topic:win386]]). That string, or a library exporting `Win386LibEntry`, among the program's files names it. The prototype looks for the string in the program and in the libraries of its folder, and runs such a program in enhanced mode. Anything else is standard mode until a run says otherwise. |
| **Display** (16 or 256 colours) | Not decidable from the files alone. A program that imports GDI's palette functions (by ordinal, from its relocations) may want 256 colours; one that only works there says so in a box or in its README. The first pass runs on the 16-colour VGA. A program that asks for more there is tried again on `vga256` ([[guide:launcher]]: a display is kept with an install). [[inferred]]                                                                     |
| **WinG**                        | A module reference to `WING`, read from the New Executable's module reference table, or `GetProcAddress` on WinG's names at run time ([[topic:wing]]).                                                                                                                                                                                                                                                                                                     |
| **Video for Windows**           | A module reference to `MSVIDEO` or `AVIFILE`; `.AVI` files in the download; a setup that installs VfW's runtime.                                                                                                                                                                                                                                                                                                                                           |
| **QuickTime**                   | `.MOV` files in the download, or a setup that installs QuickTime for Windows. Which modules a QuickTime program imports is to be read from one such program before a rule is written for it.                                                                                                                                                                                                                                                               |
| **Win32s**                      | The program's header is `PE`, not `NE` ([[topic:win32s]]), or the setup installs Win32s (its `W32SYS` and `WIN32S` files).                                                                                                                                                                                                                                                                                                                                 |
| **CD**                          | The item's form is `disc`, or the install leaves a program that reads its files from the disc's letter.                                                                                                                                                                                                                                                                                                                                                    |
| **Sound or MIDI**               | A module reference to `MMSYSTEM` or `SOUND`; `.WAV` and `.MID` files in the download; calls to `waveOut` and `midiOut` in the run.                                                                                                                                                                                                                                                                                                                         |
| **Libraries it does not bring** | Every module reference that is neither Windows' own, nor WinBox's, nor in the download (`VBRUN300`, `BWCC`, `CTL3D`, ...). The corpus leaves such programs out. The catalog records them. A runtime the first pass has (Visual Basic's, Klik & Play's, Borland's controls; "Runtimes", below) is placed for the run, and named in `runtimes`; any other missing library becomes a classification of its own.                                               |

A setup's `SETUP.INF`, or an `.INF` of its own, lists the files it copies and where, and so names the runtimes it brings (WinG, Win32s, VfW). It is read as data, never run, to fill `needs` before the install, and the install itself confirms it.

The module references are read without running anything: the New Executable header's module reference table (a word each, at 28h in the header, their count at 1Eh) points into its imported names table (at 2Ah), each name a length and its bytes. The prototype's `importsOf` reads them.

**As the first pass reads them** (`scripts/catalog/needs.mjs`):

- **The program.** The one archive.org's DOSBox starts (`run`), found in the download by its name in any case, the shallowest first. A batch file (`run.bat`, `WIN.BAT`) is read as data, and the last program it names that is in the download and not a DOS program taken: the word after `win` or `win.com`, or a word ending in `.exe`.
- **Imports.** The modules of the program and, in turn, of each library of its download that it imports; and the functions it imports, from each segment's relocation records (the segment table at 22h, 8 bytes a segment, their count at 1Ch, the alignment's shift at 32h; a segment with 0100h in its flags has its records after its data, a count and 8 bytes each, type 1 an ordinal, type 2 a name). An ordinal is named by `kb/data/exports-3.1.json`, the export tables read out of Windows' own modules.
- **Unlinked.** The functions it imports from Windows' modules that WinBox does not export (`kb/data/winbox-exports.json`): a call to one goes to `UndefDynLink`, as in Windows. A run that ends there, with any such import, is `missing`, those imports its signature.
- **`palette`**: an import of `CreatePalette`, `AnimatePalette`, `SetPaletteEntries`, `SelectPalette` or `RealizePalette` (or GDI's `GDISelectPalette` and `GDIRealizePalette`). It says the program uses palettes, not that it needs 256 colours: the run says that.
- **`sound`** an import of `MMSYSTEM` or `SOUND`, or a `.WAV` in the download; **`midi`** a `.MID` or `.RMI`. Such a program runs with WinBox's own sound card installed, as winbox-native's `--sound` installs it (`trace --sound`; [[topic:sound-devices]]).
- **`cd`**: a disc's image (`.iso`, `.cue`, `.bin`, `.mdf`, `.nrg`, `.ccd`) among the downloads or in the download; it is mounted as D: for the run. A floppy's image is mounted as A: only where the program is not in the download and so is looked for on it.
- **Setups**: the program is a setup by its name (`SETUP`, `INSTALL`, `_SETUP`, `SETUP16` and the like); the installer is Microsoft's toolkit where the download has a `SETUP.LST`, InstallShield's where it has a `SETUP.INS`, `_INST16.EX_` or `_SETUP.LIB`. A setup's `.INF` and `.LST` files are read as data for the runtimes they name (`WING.DLL`, `W32SYS.DLL`, `MSVIDEO.DLL`, `QTW.DLL`).

### Titles

archive.org's titles are poor. [[measured]] Of the 2,284, 1,311 carry the collection's prefix ("Windows 3.1 Shareware: ", 983; "Windows 3.1: ", 328), and 532 are, once it is stripped, exactly the name of the program the item runs: `win3__dare` is "Windows 3.1 Shareware: \_dare", and runs `DARE2DRM.EXE`, which is "Dare To Dream". The owner decided (2026-11-14) that a title comes from the program itself, and that MobyGames and Wikipedia are used later, only to confirm a title and link to it.

`scripts/catalog/titles.mjs` finds the candidates. archive.org's title, its prefix stripped, is kept where it is already a name, that is where the rules below do not refuse it (the owner's decision, below). Where it is a file name or empty, each source of the program's is tried in this order, and the first that gives a name is taken; the entry keeps every candidate in `titles`, and names the one taken in `titleSource`:

| Source            | What is read                                                                                                                                                                                                                                                                                                                                                                                                 |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `productName`     | The main program's version resource (type 16, from the New Executable's resource table at 24h): the `ProductName` of its first string table, in the code page the table's key names (`040904E4`: page 04E4h, 1252).                                                                                                                                                                                          |
| `fileDescription` | The same table's `FileDescription`, where it has no `ProductName`.                                                                                                                                                                                                                                                                                                                                           |
| `caption`         | The program run in WinBox for five seconds of the survey's clock, as the sample runs one, with `trace --captions`, which prints the windows at the top as the run left them, each its class, whether it is shown, whether it is one of USER's message boxes, and its caption. Taken: the first shown window not a dialog (`#32770`), else the first not a dialog, else the first shown; never a message box. |
| `fileIdDiz`       | `FILE_ID.DIZ`'s first line with words in it, read in DOS's code page 437, its frame and decoration taken off, and the part before a dash, a colon, a comma or a full stop.                                                                                                                                                                                                                                   |
| `description`     | The module description: the first entry of the non-resident names table (its file offset at 2Ch in the header, its length at 20h), the part before a dash, a colon or a comma.                                                                                                                                                                                                                               |
| `setupInf`        | A setup's `.INF` (Microsoft's setup toolkit's `[progman.groups]`): the Program Manager item that starts the program; the group's name only where the program is the setup itself, as another program's folder may hold an `.INF` not its own (one item's is Windows' own `SETUP.INF`, whose group is Main).                                                                                                  |
| `archiveOrg`      | archive.org's title, its prefix stripped. Taken first where it is a name; else the fallback.                                                                                                                                                                                                                                                                                                                 |

Then `catalog/titles.json`: corrections by hand, keyed by identifier, each a title and its reason, applied last (`titleSource` is then `correction`).

**What is split off.** A version ("v1.2", "Version 2", "1.20a") becomes `version`; a copyright notice or a year, and what follows it, `copyright`; "by" whom, `credit`. From a caption, "About " is taken off the front, what follows a dash or a spaced colon ("Notepad - [Untitled]", "UW Window : Command Protocol : 0"), a closing bracket's or parenthesis's part ("(Unregistered)") and a game's number ("Solit #233") off the end.

**What is refused**, so the next source is tried:

- a file name: one with an extension, an all-capitals 8.3 name, one with an underscore and no space, a path; or the program's, its module's or the item's own name written all in capitals or all in small letters. Written in mixed case ("DDEWatch", "BartEyes"), the program's own name is the author's spelling of it, and is taken;
- a generic word: "Setup", "Install", "Readme", "Microsoft Windows", "Windows Application", "Untitled", "Warning", "Welcome", "Standard Mode" and their like;
- not a name: a shareware notice's caption ("Please Register", "Shareware Notice", "Unregistered ..."), a setup's ("... Installation"); a compiler sample's description ("Sample Microsoft Windows Application", "My First C++ Windows program"); Visual C++ AppWizard's defaults, the project's name in capitals and "Application" or "MFC Application" ("HANOI MFC Application"); the Klik & Play runtime's own strings, which every game it made carries ("Klik & Play Stand Alone Game"); a program's state in its caption, a time ("Next Break: 01:59") or its keys ("HELP = H ...");
- a sentence, from the program's text: most of its words of four letters or more begin in small letters ("Concentration game with flags of the world"). archive.org's titles are never refused as sentences.

Where every source is refused, the title is archive.org's, stripped, file name or not.

**Code pages.** Text from a program is data: decoded in the code page its version table names, else Windows-1252, and its control characters made spaces. A text holding a byte Windows-1252 leaves undefined (81h, 8Dh, 8Fh, 90h, 9Dh), or one of the punctuation marks it puts at 80h-9Fh between two letters, was written in a DOS editor, and is read in code page 437 instead: `cmm.exe`'s module description is ",Cin‚tic Mail Manager" in Windows-1252, "Cinétic" in DOS's page. A caption is printed by `trace` a character a byte, and decoded the same way.

## Matching

A catalog entry is matched to another list's games by its title, year and publisher, by one set of rules for every list (`scripts/catalog/match.mjs`):

- **Titles** are compared without case, accents, punctuation, "for Windows", a version ("v1.2") or a bracket's part, a leading "The" or a trailing "Game", with Roman numerals as numbers. The same words score 1; the same without spaces ("SkiFree", "Ski Free") 0.95; the same main part, before a colon or a spaced dash, 0.9; otherwise Dice's coefficient over the words. Every title an entry has is tried (its title and each candidate in `titles`, archive.org's with its prefix stripped), the best kept.
- **The year** agrees within one (a release and its re-release, a list's date and archive.org's): the score is raised 0.05. More than two years apart lowers it 0.15 and is a contradiction.
- **The company** agrees where a word of a name of one side's (not "Inc", "Software", "Games" and their like) is in the other's, or begins it, four letters or more ("Saada", "SaadaSoft"): the score is raised 0.1.
- **Confident**: the best title scores 0.9 or more, nothing contradicts it, the year or the company agrees (or the title is the same exactly and neither is known), and no other candidate scores within 0.1 of it. A title of one word ("Hearts", "Golf", "Simon", many shareware games share each) needs the company to agree, or the year where no company is known on one side. An entry still titled by a file name ("BATTLES") needs both.
- **Ambiguous**: the best title scores 0.75 or more, but not confidently. These are kept with their candidates for a person to decide, and are not shown in the table.

### Wikipedia

`scripts/catalog/wikipedia.mjs` reads the "List of Windows 3.x games" as wikitext, one request through the MediaWiki API, and matches every catalog entry against its rows. Only the facts of a matched row (title, year, developers and publishers, which the list keeps in one column, and its article) are kept, in `catalog/wikipedia.json`, with the page's revision; the list is CC BY-SA 4.0, as the kb is, and the table credits it. The table uses a row's year and companies only where archive.org gives none, marked as Wikipedia's, and links to the game's article.

### MobyGames

MobyGames' terms were read on 2026-11-14 from the copies the Internet Archive keeps: its API documentation (`mobygames.com/info/api/`, as of 2026-09-12) and its API License Agreement (`mobygames.com/info/api-terms/`, as of 2025-03-12, the only copy kept). The live pages answer automated requests with a Cloudflare challenge. What they say, in brief:

- **Access.** The key is private, passed as the `api_key` query argument, and may not be shared (section 3.b). It is read from `MOBYGAMES_API_KEY` or `~/.config/winbox/mobygames-key`, and no URL holding it is printed or written.
- **Rate.** Non-commercial keys: 720 requests an hour, one every five seconds, and never more than one a second; 429 past it. Attempts to get around the limit end the licence (3.c).
- **Copies.** MobyGames' content may be copied only as an intermediate step, deleted when no longer needed (3.a.ii). Everything retrieved is MobyGames' and confidential to the licensee (5, 17).
- **Public display.** Content publicly available on MobyGames may be shown "to promote MobyGames and enable Your Users to search and browse the data", deleted when it is no longer public, and not "co-mingled or combined with non-MobyGames Content" (8.a.ii). What is shown may be at most a day older than the site, or the page says how much older it is (8.a.iii).
- **Generative AI.** Neither the site nor its content may be used, without MobyGames' written consent, "in connection with the development, training, fine tuning, grounding (including through retrieval-augmented generation (RAG)), of any large language model ... or any software or tool that incorporates generative artificial intelligence" (8.a.iv.2).
- **Publicity.** No public statement about the Developers Program without MobyGames' approval (18).
- **Attribution.** The terms ask for none in a set form; MobyGames keeps every right in its content, logos and name (5).

What that means here:

- **The API was not called.** This page, the scripts and the matching were written by an AI agent; reading MobyGames' answers to match them would be the use 8.a.iv.2 forbids without consent. `scripts/catalog/mobygames.mjs` is for a person to run, and its matches are for a person to review.
- **Only ids and links are written.** `catalog/mobygames.json` keeps, for each confident match, MobyGames' game id, its URL and the platform, and our own score; for an ambiguous one, its candidates' ids, URLs and scores. No title, year, company or other content of MobyGames' is committed or shown: the table's year and publisher are archive.org's or Wikipedia's, and MobyGames gives a link. The answers it matched from stay in `corpus/cache/catalog/mobygames/` (gitignored) until the matches are reviewed, and `--purge` deletes them.
- **Whether an id and a link may be kept in a public repository at all** is not settled by the terms (an id is "data ... retrieved from MobyGames", and the copies are to be intermediate): a question for the owner, below.

```sh
node scripts/catalog/wikipedia.mjs                # the list (fetched once), matched, catalog/wikipedia.json

```

`mobygames.mjs` searches MobyGames' titles (a substring, without case) on Windows 3.x and Windows, with up to three of the entry's titles, cleaned of brackets, "for Windows" and versions, then asks for the companies of the releases of the best three candidates whose title scores 0.9: about one to six requests an entry, five seconds apart. Its matches are the same rules' as Wikipedia's, a game's alternate titles each a candidate of its own.

## The automated first pass

Each program goes through the same steps, on WinBox, with nothing run on the host:

1. **Fetch** (`scripts/catalog/fetch.mjs`): each download of the item from archive.org, at most three at once, a request started no sooner than a second after the last, with the User-Agent "WinBox catalog" and no credentials; written to a `.part` file and resumed from where it stopped (an HTTP range); held to archive.org's SHA-1; kept in `corpus/cache/catalog/downloads/<id>/` and unpacked into `corpus/programs/catalog/<id>/` (both gitignored), a zip by the corpus's unpacker, which refuses any member whose name leaves that folder, or past 256 MiB by the system's `unzip`, which skips such members. A disc's or a floppy's image is not copied: it is mounted from the downloads' folder. The fetch stops between items once what is unpacked passes 150 GB.
2. **Read** what it needs (above): the header, the imports, the setups, `.INF` and `.LST` files, the kinds of files it brings. A program not Windows' is classified there, as is one with a library it does not bring.
3. **Install** where the program is a setup, or a setup on its disc: the setup run as Program Manager starts it (`trace --shell`, as the corpus installs Widget Workshop), on a drive kept for it. It runs first alone for 30 virtual seconds with nothing pressed, on a drive thrown away after, to find where it first waits (a box's text, else its window's caption), which Enter would answer and hide. Then again for 180 virtual seconds with Enter pressed every four, which takes each dialog's default: Continue, OK, Next, the folder offered. The program it leaves is the first item of the Program Manager groups it made ([[topic:program-manager-dde]]; the `.GRP` files it wrote, the items' command lines read from them) that is not a setup's, a help's or a text's; else, with no group, the one Windows program it wrote on the drive outside `CORPUS`, `WINDOWS` and the setup's own temporary folders. That is run next, from the drive the install left. Where it leaves none, the status is `installer`, its signature where it first waited if that was a box, else how the setup's run ended and what it showed last, with the DOS functions it asked that WinBox did not answer.
4. **Run** for ten virtual seconds on the survey's clock, from `C:\CORPUS\<ID>\` (the whole of its download copied there, on a drive made for the run) on the 16-colour VGA in standard mode, as the corpus does, with Enter at up to three of USER's boxes; in enhanced mode where the Win386 supervisor is among its files; with WinBox's sound card where it needs sound. The seconds are instructions run (3,000 a millisecond, each call charged 15; [[topic:timing]]), not the host's time, so the same commit gives the same answer every time. A program still `running` at its ten seconds is run again from the start for 20, 40, 80 and at most 120 seconds, stopping at the first length at which it is not `running`; its status is that run's, and `seconds` in its record says which length (a state reached at or before it, and after the length before). A run whose box or windows say it needs enhanced mode ("enhanced mode", "386 enhanced") is run again in enhanced mode, and one that says it needs more colours ("256 colors", "SVGA") again on `vga256`, unless it reached `idle`.
5. **Classify** the run, from what `trace` printed: the line saying why it stopped, the faults KERNEL reported, its last calls, and the windows it left (`trace --captions`, with a message box's text).

**How they are placed.** `scripts/catalog/runtimes.mjs --fetch` fetches each into its own folder of the gitignored `corpus/cache/catalog/runtimes/<module>/`: a whole file held to archive.org's SHA-1, a member of an archive or a disc's image through archive.org's view of it; every file held to the SHA-1 and SHA-256 `catalog/runtimes.json` records. The files are read only as data (their headers, entry tables and version resources) and run only inside WinBox. When a program's needs name a module the pass has a runtime of, and the program does not bring it (`needs.mjs`), the module is a runtime of the program's, not a library missing; so, in turn, is each runtime that runtime imports and the program does not bring (`KNPG` imports `KNPS`; the eleven games that lack only `KNPG` bring their own `KNPS`). The runtime's imports and functions count as the program's (`KNPG` imports `MMSYSTEM`: such a game runs with WinBox's sound card). `pass.mjs` copies the runtimes into the run's drive as `C:\WINDOWS\SYSTEM\<MODULE>.DLL`, over the installation beneath it, before the program runs, and before a setup runs; they are where an installed copy of Windows would have had them. The program's result names them (`runtimes`), and the table says "with VBRUN300". `library` is kept for the libraries still missing. A module counts as brought only where the download has its `.DLL`, the name KERNEL looks for (`KRNL386.EXE` seg2 `197d`-`1988`): a `VBRUN100.EXE` beside a program, Microsoft's self-extracting distribution, is not `VBRUN100`, and the runtime is placed (Loan Mate).

**What an item's batch file copies.** archive.org's DOSBox mounts an item as C:, the current drive, and Windows as D:, and an item's batch file often copies what a setup would have installed into Windows' folders before it starts the program (`COPY WAVEMIX\WAVMIX16.DLL D:\WINDOWS\SYSTEM`, `copy C:\WINDOWS\SYSTEM\*.* D:\WINDOWS\SYSTEM`). `pass.mjs` reads the batch as data and makes each copy from the item (C: or no drive) into a `\WINDOWS` or `\WINDOWS\SYSTEM` folder, of a name or `*.*`, into the run's drive's (2026-11-16: Comet Busters and Nuclear Winter's `WAVMIX16`, Personal Calendar's `BTTNCUR`, Omar Sharif's Bridge's settings). Other lines (a `PATH`, a `D:` source) are not followed. `trace` prints each of USER's system error boxes a run brought up (`answered:`), and the retry on 256 colours or in enhanced mode reads them as it reads a box left up, so a program that shows its box and ends is run again where it asked (Palette Test's "Display does not support a Palette (256 color driver)").

### What is committed

For each program and each run, a record: the status, the signature, the needs, the WinBox commit it ran on, and the date. It goes in `catalog/results.json`, one line per program, replaced when the program is run again. Nothing of the program is kept: no screen, no call log, no file. Those stay in the gitignored `corpus/cache/catalog/` of whoever ran it, so they can be compared on the next run.

### The work queue

Failures are grouped by signature, and the groups sorted by how many programs each holds: "`USER.Foo` missing, 37 programs", "fault in `WIN87EM` at ..., 12 programs". Each group is a piece of work for the knowledge base's usual method, a read-out and a probe before any change ([[guide:contributing]]). When a commit fixes a signature, the programs that had it are run again, and those that now get further join whatever group they reach next. The queue is made from `catalog/results.json` by a script, and shown on the site (below). It is never edited by hand.

## Human verification

`idle` says a program started. Whether it can be played or used takes a person. A rating is one of:

- **perfect**: no difference from Windows that the person saw;
- **playable**: usable from start to end, with small differences (a colour, a sound, timing);
- **runs with problems**: it runs, but something that matters is wrong or missing;
- **fails**: it cannot be used.

Each rating carries the WinBox commit it was made on, the display and mode, the date, a note, and who made it (a name they choose, or none). A rating made on an older commit is shown as such, and is a reason to look again, not a result.

The owner decided (2026-11-14): ratings are files in the repository, added by pull request. A rating is reviewed like any other change, sits next to the commit it was made on, and is published under the kb's licence with everything else. A page people fill in may be added later as a way in that ends in a file.

### Ratings

`catalog/ratings/<id>.json`, one file for each program rated, named by its catalog id; the file holds a list, so a program rated again keeps its earlier ratings. The table shows the latest by date.

```json
{
  "ratings": [
    {
      "rating": "playable",
      "commit": "1172e53a",
      "date": "2026-11-14",
      "note": "Played three rounds to the end. The shareware box comes up first, as on Windows; the sound of a win is missing.",
      "rater": "a name or handle",
      "display": "vga",
      "mode": "standard"
    }
  ]
}
```

| Field     | What it holds                                                                                                                | Required |
| --------- | ---------------------------------------------------------------------------------------------------------------------------- | -------- |
| `rating`  | `perfect`, `playable`, `runs with problems` or `fails`, as above.                                                            | yes      |
| `commit`  | The WinBox commit the program was used on (`git rev-parse --short HEAD`): 7 to 40 hexadecimal digits, in small letters.      | yes      |
| `date`    | The day it was used, `YYYY-MM-DD`; not after today.                                                                          | yes      |
| `note`    | What was tried and what was seen, 1 to 1,000 characters: how far it was played or used, and what differed from Windows.      | yes      |
| `rater`   | A name or handle the rater chooses, 60 characters at most. Never an email address: one is refused. Left out to be anonymous. | no       |
| `display` | `vga` (16 colours) or `vga256`.                                                                                              | no       |
| `mode`    | `standard` or `enhanced`.                                                                                                    | no       |

No other field is accepted. `scripts/kb/compatibility.ts` checks every file when the site builds (`validateRatings`), so the pre-commit hook, which builds the site, refuses a file that is not sound, and `npx jest test/kb` tests the rules.

**To add a rating:** run the program in WinBox at a commit you name, use it as a person would (a game played through a level or more, an application's document opened, edited and saved), and compare it with Windows where you can. Find its id in `catalog/catalog.json` (the table's archive.org link ends with it). Add your rating to `catalog/ratings/<id>.json`, making the file if it is not there, run `pnpm kb`, and open a pull request.

## Publishing

The owner decided (2026-11-14) that the table is public on the kb site from the start. It is built: `pnpm kb` writes `/compatibility/` (`scripts/kb/compatibility.ts`) from `catalog/catalog.json`, `catalog/results.json` and `catalog/queue.json` where the first pass has written them, `catalog/ratings/`, and the matches in `catalog/wikipedia.json` and `catalog/mobygames.json`. A program the first pass has not reached yet is shown as not run; the results may be missing, empty or partial, and are read as a list, an object of `items`, an object keyed by id, or a record a line.

Its columns: the title; the year and publisher (archive.org's, else Wikipedia's, marked so); the kind; the needs; the first pass's status, with its signature and the commit and date it ran on; the latest rating, with its commit, date and rater; and links. The links are the archive.org item, where the program is published (never a copy of it); MobyGames' page and Wikipedia's article, where matched confidently; and "why", the kb page or probe that explains a failure: the one the work queue names for its group, else the function's own page for `missing` and [[topic:win32s]] for `win32s`.

It is one plain table, sorted by title, that reads without a script. A short script of the page's own sorts it by any column's heading (a button, its order in `aria-sort`), and narrows it by words, kind, status and rating; a line read out to screen readers says how many rows are shown. Each link names its program for a screen reader ("Solus on archive.org"). At 2,245 rows the page is about 1 MB.

The work queue is to be a second page, the signatures sorted by how many programs each holds.

## The prototype

```sh
node scripts/catalog/catalog.mjs            # list, fetch metadata not yet cached, write catalog/catalog.json, count
node scripts/catalog/catalog.mjs --counts   # count the catalog already written
cargo build --release -p winbox-win16 --example trace
node scripts/catalog/sample.mjs             # ten games, fetched, run and classified
node scripts/catalog/titles.mjs --filenames # the items titled by a file name: fetched, read, run for their captions
node scripts/catalog/titles.mjs --fetched   # every item fetched so far read again, without a run
node scripts/catalog/catalog.mjs --titles   # the titles chosen again, and the catalog written
```

`catalog.mjs` lists the collections with archive.org's advanced search, then asks the metadata API for each item, half a second apart, with the User-Agent "WinBox catalog" and no credentials. Each item's answer is cached in `corpus/cache/catalog/` (gitignored), so running it again only asks for new items. `sample.mjs` chooses loose games of DOSBox's, in a single zip of at most 3 MiB and not already in the corpus, in the order of their identifiers' SHA-1 (a spread that is the same each time, not picked by hand). It fetches them through `fetch.mjs --manifest`, checks archive.org's SHA-1, reads each program's header and module references, runs it with `trace` as the corpus does, and classifies the run. Its traces and screens stay in `corpus/cache/catalog/`. `titles.mjs` fetches with the same User-Agent and pause, holds each download to archive.org's SHA-1, unpacks it with the corpus's unpacker into `corpus/programs/catalog/<id>/`, and keeps what it finds of each item in `corpus/cache/catalog/titles/<id>.json`, the run's windows with it, from which `catalog.mjs --titles` chooses; all of it gitignored. Only the chosen title and the short candidate strings reach the catalog.
